# F5 traceability — beads → katra migration

Every acceptance criterion from the F5 spec (`bd show katra-9aw.49`), mapped
to the named test that would fail if the behaviour regressed. Same
convention as [`f4-traceability.md`](f4-traceability.md): the column on the
right is the point of the document, not the tick — a criterion whose "test"
cannot fail is not covered, and saying so is more useful than pretending
otherwise. Two rows below (8 and 9) are exactly that case, and say so
explicitly rather than citing a test that doesn't exist.

Test names are quoted exactly as they appear in the suite, so `vitest -t`
finds them. `(core)` and `(cli)` disambiguate same-named files. The
per-category fixture map — which planted record proves which
`MigrationReport` category, at which exact count —
is [`test/fixtures/beads-full.md`](../test/fixtures/beads-full.md); this
document does not repeat that detail, only points at it.

## Mutation notes

Unlike F4's pass, F5's implementation and validation ran as one continuous
thread across seven rounds (initial build, an efficiency-review pass, a
senior branch review, a residuals pass, a targeted bugfix, an independent
security scan, and a QA pass), and falsifiability was checked by hand at
nearly every step rather than after the fact — the same agent that wrote
each fix ran the "break it, watch the named test fail, revert" cycle for
it. What follows is a representative selection, not an exhaustive log of
every one; the ones below are the ones that found something interesting on
the way, not just confirmed the obvious.

**Graph logic (`transform.ts`), initial build:**
- Swapping `taskOldId`/`dependsOnOldId` when building a dependency `PlannedEdge` failed "maps blocks edges…" and, separately, made `bf-open-dependent` in the fixture read as blocked by nothing real — the mutation cited in row 4 above.
- Reversing `breakBlocksCycles`' sort comparator changed *which* edge a real cycle drops — failed "detects and deterministically breaks a blocks cycle, reporting the dropped edge" with the wrong edge named. Simply *removing* the sort did **not** fail this test, because the fixture's own input order happened to already match sorted order — a false negative caught only by trying the reversal too, which is why row 4's citation and the QA-round citation below both use reversal, not removal.
- Injecting `Math.random()` into the plan-local note id generator failed "produces identical output for identical input" — the one test whose entire job is catching non-determinism.

**Efficiency review (memoized ancestry walk, widened shape gate):**
- Corrupting the ancestry cache's mid-walk hit branch (returning the wrong cached value) failed "flattens a three-deep chain…"; corrupting the epic-found branch failed a dedicated 8-deep-chain memoization test — two different mutations for two different cache-population code paths, neither redundant with the other.
- Removing `hasValidShape`'s new `owner`/`created_by`/`external_ref`/`started_at` checks reproduced a real `TypeError` thrown out of `planMigration` for a hostile record, rather than a clean `invalidItems` entry.

**Targeted bugfix (`katra-9aw.49.10`, double-counted `invalidTimestamps`):**
- Reverting *both* halves of the fix together (`transform.ts` back to passing the raw `created_at`, `mapping.ts` back to re-normalizing it) reproduced the exact reported bug: one bad issue-level timestamp counted twice. Reverting only one half at a time did **not** reproduce it — `mapIssue` already substitutes the fallback for a bad value before `assembleNotes` ever sees it, so a lone re-normalize call downstream just re-parses an already-valid string with zero degradations. The fix is more robust than a minimal patch would have been, which the two-part mutation is what surfaced.

**Senior branch review (SQL-bind shape gate, coherence guard, link dedupe):**
- Removing the `description` type check failed **both** a dedicated unit test and `f5-feature.test.ts`'s exact-count assertion (3 → 4 `invalidItems`) — the only mutation in this project that failed a unit test and an e2e count assertion in the same run.
- Disabling the converse `!markClosed && isTerminal(lane)` guard in `applyMoveWithin` is the standout: the test then failed with a raw `CHECK constraint failed: lane NOT IN ('Done','Cancelled') OR closed_at IS NOT NULL` — exactly the un-decoded SQLite error the guard exists to turn into a typed `internal` refusal, caught live rather than reasoned about.
- Un-sorting the link-pair dedupe key (comparing the raw pair instead of the alphabetically-sorted one) failed "collapses link pairs regardless of type or direction…" — link count came back 2 instead of 1.

**Security scan (bounded cycle paths, ISO timestamp gate):**
- Removing the `MAX_CYCLE_PATH` slice on a 40-node synthetic parent cycle failed the truncation test with path length 41 instead of 32 — the exact shape of the O(n²) growth the fix bounds.
- Removing the `ISO_INSTANT_PATTERN` gate ahead of `Date.parse` failed both new tests, reproducing the raw defect: an expanded-year string (`"+275760-…"`) and a locale-grammar string (`"Dec 25 1995"`) both parsed successfully instead of being classified invalid.

**QA pass (coverage gaps, test-only):**
- Disabling one `hasValidShape` field check (`issue_type`) failed exactly one `it.each` case out of thirteen, leaving the other twelve green — proof the table's cases are independent, not accidentally redundant.
- Removing `routeEdgesByType`'s fallback for an unrecognised edge type made it drop silently instead of landing in `danglingEdges` — failed the dedicated test for that branch.

Every mutation above was reverted immediately after observing the failure,
confirmed via `diff` against a saved known-good copy of the file before
moving on — none of this evidence is inferred from reading the code.

## Known limits

- **`--from`'s 32 MiB size-cap path is accepted-untested.** `readExportFile`'s `stats.size > MAX_FROM_BYTES` check is a plain comparison against a `statSync` result — writing a 32 MiB fixture file on every test run to exercise one `if` was judged not worth the cost. Documented directly in `migrate.test.ts`'s own module docstring; exercised manually during the security review that set the cap, with measured evidence (extract.ts's own module docs record the memory blowup a much larger file would cause before this guard existed).
- **Two permission-error catch branches in `readExportFile` are untested.** The non-`ENOENT` branch of the `statSync` catch (permission denied, a broken symlink, an I/O error) and the `readFileSync` catch (a mode change between the stat and the read) both exist for real failure modes, but neither has a named test — reliably provoking `EACCES` requires root-independent file permission tricks that don't run the same way in every CI sandbox. Filed as part of `katra-9aw.53`.
- **`MAX_ANCESTRY_DEPTH`'s truncation path is untested.** `walkAncestry` gives up after 10,000 parent-child hops and reports through the same `cyclePath` arm a real cycle uses (see `transform.ts`'s own docs) — unlike `MAX_CYCLE_PATH`, which has a dedicated 40-node test (`beads-transform.test.ts` — "caps a large parent cycle's reported path and marks it truncated", cited in the mutation notes above), nothing constructs a 10,000-node acyclic chain to prove this specific bound fires. The code path is a straightforward length check patterned identically on the tested one; still, "identically patterned" is not "proven."
- **Three follow-ups filed during validation, deliberately not fixed on this branch:**
  - `katra-9aw.51` — `breakBlocksCycles` runs one BFS per candidate edge (O(E·(V+E))); a dense acyclic `blocks` graph at the 32 MiB `--from` cap could cost minutes of pegged CPU during a preview that ends in an empty report. Real corpora are nowhere near the threshold that matters; filed as a performance follow-up, not a correctness bug.
  - `katra-9aw.52` — `loadMigration`'s empty-store refusal checks the `tasks` table only. Since events outlive their tasks by design (ADR-008), a store whose tasks were all deleted would pass the refusal, and migrated historical events would land on top of surviving real history — `katra log` orders by `events.id`, so beads history would read as the newest activity. Audit-trail contamination only; the transaction boundary itself holds regardless. Filed as a decision (widen the refusal to events, or document the narrower scope) rather than resolved on this branch.
  - `katra-9aw.53` — `breakBlocksCycles`' adjacency-accumulation line (`existing.push(...)`) is exercised by the two-prerequisite test (this document's row 2 supporting evidence, `beads-transform.test.ts`), but a third edge, sorted to process last, would prove the accumulation specifically — a two-edge case can pass even if `existing.push` silently became `adjacency.set` (overwrite instead of accumulate), since nothing downstream re-checks the first blocker. Filed as a targeted test gap, low severity: `addDependencyWithin` re-runs its own cycle check at write time, so a real regression here would throw at `--apply` — breaking the "clean preview predicts apply" promise loudly — rather than silently corrupting data.
- **The timestamp gate accepts `Z`-suffixed UTC only, by design.** `ISO_INSTANT_PATTERN` requires a literal trailing `Z`; a technically-valid ISO-8601 timestamp with a numeric offset (`"2026-08-03T09:05:00+02:00"`) does not match it and degrades to the reported-and-substituted `invalidTimestamps` fallback path, same as any other unparseable value. This is deliberate, not an oversight — `bd export` only ever emits `Z`-suffixed UTC timestamps (verified against this repository's own real export and beads 1.0.4's documented behavior), so the narrower grammar is the correct gate for the actual input space, not an accidental restriction that happens not to bite yet.
