# F6 traceability — search, recent, stale

Every acceptance criterion from the F6 spec (`bd show katra-9aw.54`), mapped
to the named test that would fail if the behaviour regressed. Same
convention as [`f5-traceability.md`](f5-traceability.md): the column on the
right is the point of the document, not the tick — a criterion whose "test"
cannot fail is not covered, and saying so is more useful than pretending
otherwise. Row 8 is exactly that case in miniature: solid coverage with one
honestly-named gap, not a blanket pass.

Test names are quoted exactly as they appear in the suite, so `vitest -t`
finds them. `(core)`, `(cli)` and `(e2e)` disambiguate same-named files —
`(e2e)` is `test/cli/f6-feature.test.ts`, the whole-story file that composes
several real commands against one store, the same role `f4-feature.test.ts`/
`f5-feature.test.ts` play for their features.

## Mutation notes

F6's build ran across seven distinct rounds on one continuous branch
(initial implementation, a senior + efficiency review, a residual re-review,
Validate's senior branch pass, an independent security scan, a QA pass, and
this documentation pass), and — like F5 — falsifiability was checked by hand
at nearly every step: the agent making each fix ran the "break it, watch the
named test fail, revert" cycle immediately, confirming the revert against a
byte-identical saved copy before moving on. What follows is every mutation
run during that work, not a curated sample — F6's build was smaller than
F5's, so the full log is short enough to include whole.

**Initial implementation (`readSearch`'s rollup, T5):**
- Swapping the outer `ORDER BY` to read the winning row's own `id_match` instead of the `id_match_any` window aggregate failed "keeps idMatch true for a task matching both by id and by text" — the exact any-row-property regression the rollup's pinned SQL shape exists to prevent.
- Column-scoping the `tasks_fts` branch's `MATCH` to `title: (...)` failed "finds a task whose terms are split across title and description" — the cross-column recall case plan-review rejected before this shape ever shipped.
- Reversing the `src_rowid` tiebreak direction (`ASC` to `DESC`) in the partition `ORDER BY` failed "rolls tied-tier note hits to the best-scoring one deterministically", flipping which note won. Simply *dropping* the tiebreak term did **not** fail it, even across three repeated runs — SQLite's own scan order happened to coincide with what the tiebreak would have chosen — which is exactly why a second, SQL-text-level structural assertion exists for this same property (added in the senior-review round below): the drop-mutation is invisible to any behavioral test under this schema, and only a structural one catches it.
- Switching `activityJoin` from outer to inner on both paths failed "carries lastActivity on text-path hits, null for an event-less task" and "keeps a task with no events on the filter path with null last activity, sorted last" — the event-less task disappeared from the results entirely instead of reporting `lastActivity: null`.

**Senior + efficiency review (ranking and boundary residuals):**
- Flipping `score ASC` to `score DESC` in the outer `ORDER BY` failed "orders same-tier hits best-bm25-first" — the better (more negative) match sorted last instead of first.
- The `id_match_any`-vs-`id_match` swap again, this time against a dual id-and-text match rigged so its *own* text score is deliberately worse than a text-only competitor's: failed "ranks a dual id-and-text match above a text-only competitor even when the dual's own text score is worse" — a stronger proof than the first round's, since it shows the `ORDER BY` term itself decides the ranking, not merely that the reported flag is correct.
- Changing `snippet()`'s column index from `-1` (auto-select) to `0` (title only) failed the exact-string snippet pin in "finds a task by a description-only word…" — the wrong, unmarked column rendered.
- Relaxing `activityCutoff`'s strict `<` to `<=`, and separately `>` to `>=`, each independently failed "puts an activity exactly on the cutoff outside both updatedBefore and updatedAfter windows" at the matching assertion.
- Dropping the `src_rowid` tiebreak from the partition `ORDER BY` (mutation repeated from the initial round, to confirm) again left the behavioral tied-tier test green; the new structural test — "pins the rollup's ORDER BY clauses structurally, not just their observed outcome" — is what actually failed on the drop, by inspecting the prepared SQL text directly via a `Database.prototype.prepare` spy.

**Validate's senior branch pass (render truncation, id-fragment trimming and collision rate):**
- Dropping `formatSearch`'s `truncated` check on its empty branch reproduced the reported bug exactly: `"no matches for zephyrus"` printed under `--limit 0` against a genuinely non-empty ranking.
- Reverting `idFragment(query.trim())` to the untrimmed call failed "still ranks the id hit first when the query is padded with whitespace" — the id hit vanished from the results entirely, not merely its `idMatch` flag.
- Reverting the id-fragment classifier's split minimum (bare input back to the same floor as an explicit `kt-`-prefixed one) failed "classifies plausible id fragments and rejects the rest" at the new assertions — an ordinary two-letter word (`"db"`) classified as a plausible id fragment again.

**Security scan (query-echo bound, snippet marker escaping):**
- Dropping the clamp on `formatSearch`'s zero-hit query echo failed "returns zero hits, not an error, for punctuation-only queries" at its long-query assertion — a 500-character query rendered as a 516-character unclamped line.
- Removing the quote-doubling escape from `snippetSql`, combined with injecting a literal quote into a marker constant, reproduced a real `SqliteError: near "probe": syntax error` — restoring the escape with the identical injected marker executed cleanly, proving the hazard and the fix against the same input.

**QA pass (truncation coverage, CLI flag wiring, calendar validity):**
- Swapping `formatSearch`'s `RAISE_SEARCH_LIMIT_LINE` for the time-shaped `RAISE_LIMIT_LINE` failed only search's own new truncation test, leaving `recent`'s and `stale`'s green — proof the two hint constants are independently pinned per command, not accidentally sharing one that happens to read correctly for two of the three.
- Applying the QA reviewer's own prescribed mutation to `formatStale` (drop the `truncated` check on its empty branch) reproduced the identical bug class as `formatSearch`'s: `"nothing is stale"` printed under `--limit 0` over a genuinely non-empty result.
- Swapping `--epic`/`--tag` routing in the CLI command's option-to-`SearchOptions` mapping failed "wires --kind/--level/--epic/--tag through to real filters…" at the epic assertion (`expected [] to include '...'`).
- Dropping the calendar round-trip check in `parseWhen` failed "refuses a calendar day that does not exist…" — `"2026-02-30"` parsed to March 2nd instead of refusing, the exact `Date.parse` rollover leniency this module exists to keep out of a stored timestamp.

Every mutation above was reverted immediately after observing the failure,
confirmed via a byte-identical diff against a saved copy of the file before
the next one began.

## Known limits

- **`unicode61`'s tokenizer boundaries are accepted, not solved** (ADR-013's Consequences section). Emoji are treated as separators, not indexed content, so an emoji-only query never finds anything; CJK text is not word-segmented (a whole run of Han/Kana/Hangul characters is one token), so a CJK title is findable by prefix but not by an internal sub-word the way a space-delimited language is.
- **The 32-token cap on a query is fail-open by design, not fail-closed.** `matchExpression`'s `MAX_TOKENS` truncates an oversized query to its first 32 terms rather than refusing it — and because every token is one more AND-ed constraint, dropping the trailing ones makes the match *broader*, not narrower. A caller reasoning about this as a security boundary needs to read it the right way round: it is a usability trade against hanging on a pathological paste, not a limit on how much a query can match. Documented in `matchExpression`'s own docstring (`search-query.ts`), with the measured cost curve that motivated the cutoff.
- **The "note match — " prefix a text render shows is a display hint, not provable provenance — `matchedIn` in `--json` is the field a consumer should actually trust.** `snippet()`'s own markers (and, in principle, a stored title or note body) can contain the identical literal characters the marker uses (probe-verified during T1's research), so a hostile or coincidental stored string could make a rendered line *look* like it carries a provenance marker it does not structurally have. The structured `matchedIn: "task" | "note"` field never has this ambiguity — it is a value computed by the rollup's own SQL, not text pattern-matched out of a rendered string.
- **Four defensive throws in `search.ts`'s row-narrowing are unreachable by construction, and untested.** `narrowMatchedIn`, `narrowIdMatch`, `narrowNullableScore` (via their shared `invalidColumn` helper) exist to catch a malformed `matched_in`/`id_match`/`score` column — but every row search.ts's own SQL produces is guaranteed to already satisfy those shapes, so no test constructs the malformed input that would exercise the throw branch itself. This is the entire gap behind `search.ts`'s 94.8% statement coverage (everything else in the F6 surface — `search-query.ts`, `activity.ts`, migration 0004, and every CLI command — is at 100%); the same discipline `narrow.ts`'s own columns follow for a genuinely untrusted stored value, applied here to a value this module authors itself.
- **A hyphenated query is phrase (adjacency) semantics, not independent-term semantics.** `matchExpression` phrase-quotes each *whitespace-separated* token as one unit — so `beads-migration`, typed with no space, becomes one phrase-quoted token, and `unicode61` (which drops the hyphen as a non-word separator during indexing) requires "beads" immediately followed by "migration" to match it. Text where the same two words appear non-adjacently — "beads are used in the migration process" — does not match. Verified against this repository's own real dogfood corpus (T8): `search beads-migration` correctly returns no matches for text that reads "beads → katra migration" with other words between them, and does not crash — the pre-F6 world threw `SqliteError` on this exact input (bareword `MATCH` parses an unescaped hyphen as column-filter syntax); this is the safe, documented behavior that replaced it, not a new regression.
- **`--updated-before`/`--updated-after` exclude a task with zero events**, because `activityJoin`'s outer join reports `lastActivity: null` for one, and `NULL < ?` / `NULL > ?` are never true in SQL. Every task `add` creates gets a `created` event, so in practice this can only affect a task that predates migration 0002 (when the `events` table was introduced) and has never been touched since — a real but narrow case, not something an ordinary store built entirely under F6-and-later ever produces.
- **`snippet()`'s display markers can collide with identical literal characters already present in the stored text.** Probe-verified during T1's research and stated directly in `SearchHit.snippet`'s own contract docs: the markers are display-best-effort only, not a structural promise `--json` consumers (or a text renderer trying to parse them back out) should rely on.
